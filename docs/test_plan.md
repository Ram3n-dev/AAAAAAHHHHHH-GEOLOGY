# Тест-план (PoC)

Версия 0.2 · 09.10.2026 · Ответственный: Жалсапова Б.Б.
Статус: подготовлен план тестирования и перечень проверок. Проведена предварительная автоматизированная проверка CSV; командная приёмка данных ещё не завершена. 
Подробные шаги тест-кейсов дополняются по мере готовности проверяемых компонентов.

## 1. Назначение

Документ описывает, что, как, кем и когда проверяется в прототипе GeoLens, и по каким условиям прототип считается готовым к защите.

## 2. Объект тестирования

Прототип GeoLens (семестр 1): одна страница с картой площади Енисейского кряжа, слоями данных, картой перспективности и объяснением оценки по клику на ячейку.
Состав: скрипты подготовки данных, модель и базовый алгоритм, API (FastAPI), веб-интерфейс, развёртывание (Docker Compose).

## 3. Что тестируем и что нет

Тестируем:
- требования ФТ-1 … ФТ-8 и НФТ-1 … НФТ-7 (requirements.md)
- критерии приёмки PoC П-1 … П-7 (acceptance.md)

Не тестируем (вне PoC):
- загрузку пользовательских данных, авторизацию, несколько пользователей
- экспорт в GeoTIFF / shapefile
- работу на мобильных устройствах
- нагрузку больше одного пользователя

## 4. Виды проверок

| Блок | Что проверяем | Исполнитель | Проверяющий |
|---|---|---|---|
| Данные | проекция, сетка, границы, отсутствие пропусков, воспроизводимость скрипта | Роман | Анна |
| Модель | блочная кросс-валидация, сравнение с базовым алгоритмом и случайным ранжированием, признаки утечки | Анна | Роман |

Правило: задача принимается, только когда её проверил не автор.

## 5. Окружение

- Браузер: Yandex browser, последняя версия
- Запуск: Docker Compose на ноутбуке члена команды (ОС: Windows 11)
- Данные: открытые слои по площади 58.5–60.6° с. ш., 92.3–95.0° в. д., сетка 1 км
- Инструменты: QGIS и gdalinfo для проверки данных; Swagger (FastAPI) для проверки API

## 6. Критерии начала и окончания

Начало тестирования блока:
- функция влита в основную ветку
- автор сам проверил её и написал, как запустить

Окончание тестирования PoC:
- все тест-кейсы с приоритетом «высокий» пройдены
- нет открытых дефектов с серьёзностью «критический» и «высокий»
- все пункты П-1 … П-7 в acceptance.md отмечены

## 7. Дефекты

Дефекты заводятся как Issues в репозитории с меткой `bug`.

Шаблон:
- Что делали (шаги)
- Что ожидали
- Что получили (скриншот или текст ошибки)
- Серьёзность: критический / высокий / средний / низкий
- Связанный тест-кейс и требование

Серьёзность:
- **критический** — система не запускается или падает
- **высокий** — не работает функция из требований
- **средний** — функция работает с ошибкой, есть обходной путь
- **низкий** — оформление, опечатки

## 10. Риски тестирования

- Функции появляются поздно (недели 12–13), на тестирование остаётся мало времени → тестируем данные и API раньше интерфейса.
- Проверяющий занят своей задачей → проверка чужой задачи планируется в понедельник вместе с остальными задачами недели.
- Нет независимого эксперта-геолога для оценки результата → результат проверяется по метрикам (П-4) и научным руководителем.
